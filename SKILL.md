# Clear Goal Skill — постановка целей для AI-агента

## Назначение
Помогает пользователю сформулировать цель для AI-агента (через `/goal` или обычный промпт).
Превращает хаотичные мысли в чёткую цель с проверяемыми критериями, ограничениями и анализом рисков.

## Когда применять

**Применять, если выполнено хотя бы одно:**
- Явная команда: `/цель`, `/goalhelp`, «сформулируй цель», «проясни задачу», «помоги поставить цель»
- Описана работа, но **нет конкретного объекта** (файла, модуля, команды)
- Описана работа, но **нет критерия готовности** (чем проверить результат)
- В одном сообщении **несколько несвязанных идей** («и ещё надо…», «а также…»)
- Запрос подразумевает длительный автономный прогон (агент будет работать много ходов)

**НЕ применять:**
- Цель уже чёткая: есть объект + критерий проверки → подтвердить и переходить к делу
- Вопрос на знание, объяснение, ревью, поиск («что такое…», «почему…», «посмотри…»)
- Одношаговое действие: прочитать файл, запустить одну команду, мелкая правка
- Пользователь явно просит «просто сделай, без вопросов»

## SMART+STRONG — 7 критериев качественной цели

### S — Specific (Конкретика)
Что именно делаем? Какой объект, файл, модуль, проект?
- Хорошо: «Починить билд в `components/SkillCard.tsx`»
- Плохо: «Сделать чтобы работало»

### M — Measurable (Измеримость)
Как агент понять, что цель достигнута? Обязательный критерий Done.
- Команда с exit 0: `npm run build`, `npx tsc --noEmit`
- Файл появился/изменился: `TASKS.md` обновлён, `PROJECT_SUMMARY.md` создан
- Статус: задачи в `TASKS.md` переведены в `✅`

### A — Achievable (Достижимость)
Реалистична ли цель? Что может помешать?
- Зависимости (npm, env, доступы, API-ключи)
- Объём работы в рамках одного goal-цикла

### R — Relevant (Релевантность, Outcome)
Зачем это нужно и какую ценность даёт?
- Не «потому что надо», а «чтобы X стало Y»
- Формулировать как итог для пользователя, а не как техническое действие

### T — Time-boxed (Ограничения по ресурсам)
Не бесконечная цель. Лимиты:
- `--max-turns N` — количество авто-продолжений
- `--max-minutes N` — время
- `--max-cost N` — бюджет токенов (если применимо)

### S — Strategy/Resources (Ресурсы и среда)
Что нужно для старта:
- Env (node, python, npm, конкретные версии)
- Доступы (репозитории, API, БД)
- Конкретные файлы/скрипты для запуска
- Зависимости `npm install` или `pip install`

### T — No-waste (Не трогать лишнее, хирургичность)
Чего делать НЕЛЬЗЯ (и это важнее, чем «делать»). Явный список файлов,
модулей и зависимостей под защитой:
- Файлы/папки под защитой (не удалять, не менять)
- Тесты не на рабочих данных
- Удаление — только обратимым способом, принятым в проекте (см. `AGENTS.md`)
- Не ломать текущее (non-goal)
- **Read-only правило: «проверь» ≠ «измени».** Просьба проверить, посмотреть или
  оценить не даёт права менять файлы — применяется всегда, без исключений

## Алгоритм работы (один, универсальный)

### Шаг 0 — Читаем контекст проекта
```
Если есть AGENTS.md в текущем проекте — прочитать его первые 200 строк.
Извлечь: правила безопасности (удаление, кодировки, test/данные, удаления в корзину, temp/).
Эти правила добавим в constraints и non-goals автоматически.
```

### Шаг 1 — Сбор фрагментов
Пользователь кидает что есть (фразы, мысли, недоделанное описание).
Агент:
- НЕ перебивает, НЕ спрашивает сразу
- Собирает всё, что есть, в черновик
- Если цель ОЧЕНЬ простая (1 фраза, 1 файл, 1 команда) — можно сразу к Шагу 5

### Шаг 2 — Структурирование
Формирует черновик из фрагментов:
- Что делаем (объект, файл, модуль)
- Зачем (ценность)
- Что уже понятно

### Шаг 2.5 — Расщепление составных целей

Признаки, что целей на самом деле несколько:
- Objective не умещается в одно предложение без союза «и», соединяющего два
  разных результата
- Критерий Done приходится склеивать через `&&` из несвязанных проверок
- Части затрагивают разные модули и могут быть выполнены по отдельности
- Для одной части объект является защищённым (non-goal), а для другой — рабочим

Если признак есть — **разбей на отдельные цели**, каждая со своим критерием Done,
и предложи порядок:

```
Похоже, это две цели: 1) починить билд, 2) синхронизировать wiki.

1. Сделать последовательно, сначала билд   ← по умолчанию
2. Только первую, вторую отложить
3. Оставить одной целью
4. свой вариант
```

**Исключение — не разбивать**, если части бессмысленны по отдельности:
миграция и её откат, рефакторинг и обновление вызовов, переименование
и правка импортов. Признак: вторая часть без первой оставляет проект сломанным.

**Почему это важно:** склеенный критерий `--check "a && b"` не различает
«первое сделано, второе упало» и «не сделано ничего» — в обоих случаях
команда возвращает не-ноль, и агент не знает, что переделывать.

### Шаг 3 — GAP-анализ (автоматически, без вопросов)
Проверяет каждый из 7 критериев SMART+STRONG:

| Критерий | Проверка | Если нет → |
|---|---|---|
| S | Есть конкретный объект/файл? | Отметить в черновике |
| M | Есть команда проверки? | Отметить пустоту |
| A | Реалистично? Есть зависимости? | Отметить риски |
| R | Понятна ценность? | Отметить пропуск |
| T | Есть лимиты? | Предложить дефолты |
| S | Есть env/доступы? | Отметить пустоту |
| T | Что НЕ трогать? | Отметить пропуск |

**Ключевое правило:** если критерий заполнен (даже частично) — НЕ задавать по нему вопрос.

### Шаг 4 — Уточнения: волнами по 2, только по рискованным пропускам

**Сначала поиск, потом вопрос.** Прежде чем спрашивать, попробуй добыть ответ сам:
посмотри `AGENTS.md`, `README`, `package.json` (секция `scripts`), `Makefile`,
конфиги тестов, историю git. Спрашивать только о том, чего в проекте нет.
Найденное используй как варианты ответа.

#### 4.1 Оценка риска каждого пропуска

Для каждого незаполненного критерия оцени: **что будет, если агент угадает неверно?**

| Риск | Признаки | Действие |
|---|---|---|
| **Высокий** | Необратимые или разрушительные последствия: удаление данных, миграции БД, запись в прод, деньги, права доступа, публикация. Либо взаимоисключающие трактовки, где неверная обесценивает всю работу. Либо нет критерия Done при длительном автономном прогоне. | **Спросить обязательно** |
| **Средний** | Несколько равновероятных трактовок объекта или способа проверки. Неизвестны границы правки при автономном прогоне. Ошибка стоит заметной переделки, но обратима. | **Спросить** |
| **Низкий** | Легко откатить, дёшево исправить. Либо ответ очевиден из контекста или однозначно выводится из `AGENTS.md`. Лимиты, формат отчёта, стиль, именование. | **Не спрашивать:** взять дефолт и пометить `[от модели]` |

#### 4.2 Волны

- В одной волне — **максимум 2 вопроса**, отсортированных по убыванию риска.
- Задал 2 → дождался ответа → **пересчитал GAP-анализ заново** (ответ мог открыть
  новые пропуски или закрыть старые) → если остались пропуски среднего или
  высокого риска, задаёшь следующую волну.
- Если волна не первая — покажи прогресс: «Осталось 2 уточнения».

#### 4.3 Формат вопроса: готовые варианты по цифрам

К каждому вопросу дай **2–3 коротких тезисных варианта** и возможность написать свой.
Варианты берутся из разведки проекта (Шаг 0 и начало Шага 4), а не выдумываются.
Первый вариант — рекомендуемый по умолчанию, помечается `← по умолчанию`.
Варианты нумеруются **сквозно по всей волне**, чтобы пользователь мог ответить
одной строкой вида «1, 4» или «1, свой: только src/».

Правила к вариантам: одна строка, без пояснений, взаимоисключающие по смыслу.

#### 4.4 Когда остановиться

Остановиться и перейти к Шагу 5, если выполнено **любое**:
- Пропусков среднего и высокого риска не осталось
- Прошло **3 волны** (6 вопросов) — дальше работать на предположениях
- Пользователь ответил «не знаю» / «на твоё усмотрение» / «давай уже» **на всю волну**
  (если так отвечено лишь на отдельный вопрос — см. 4.5, остальные вопросы остаются в силе)
- Две волны подряд не изменили оценку риска (вопросы перестали помогать)

#### 4.5 Если ответа нет

Ответы «не знаю», «на твоё усмотрение», «неважно», молчание или ответ не по
существу обрабатываются одинаково:

1. Взять вариант по умолчанию из предложенных
2. Пометить значение в финальной цели маркером **`[от модели]`**
3. **Больше не возвращаться к этому пункту** ни в этой, ни в следующих волнах
4. Если дефолта нет и пропуск **высокого** риска — не угадывать: записать
   в раздел «Риски» явным текстом «не определено: <что именно>, агент действует
   консервативно» и сузить цель до части, безопасной при любом ответе

Переформулировать и спрашивать то же самое другими словами — **запрещено**.

**Маркер `[от модели]`** ставится рядом с каждым значением, которое навык выбрал
сам, а не получил от пользователя или из проекта. Пользователь должен с одного
взгляда видеть, где решение принято за него:

```
--check "npm run build" [от модели]
--max-turns 10 [от модели]
--non-goal "tests, configs"          # подтверждено пользователем, без пометки
```

#### Пример волны

```
Два уточнения, чтобы не сделать не то. Ответьте цифрами или своим вариантом.

1) Критерий Done — чем проверяем?  [высокий риск: прогон автономный]
   1. `npm run build`      ← по умолчанию (нашёл в package.json)
   2. `npm run build && npm test`
   3. `npx tsc --noEmit`
   4. свой вариант

2) Что точно НЕ трогать?  [средний риск: затрагивается shared-модуль]
   5. тесты и конфиги      ← по умолчанию
   6. только файлы вне `src/shared/`
   7. ничего не защищаем
   8. свой вариант
```

Ответ «1, 5» закрывает обе позиции. Если пользователь молчит или говорит
«на твоё усмотрение» — применяются варианты по умолчанию с пометкой.

### Шаг 5 — Сборка цели + определение формата вывода

Формирует готовый текст цели. Перед выдачей определи наличие goal-плагина
в таком порядке:

1. **Кэш сессии.** Если в этой сессии уже проверяли — взять прошлый результат,
   повторно не проверять.
2. **Чтение конфигов** (читать файлом, кроссплатформенно). Проверить проектный
   и глобальный, оба расширения:
   - `./opencode.jsonc`, `./opencode.json`, `./.opencode/opencode.json`
   - `~/.config/opencode/opencode.jsonc`, `~/.config/opencode/opencode.json`
   - Windows: `%USERPROFILE%\.config\opencode\`

   Искать `goal` **только внутри секции `plugin`**, а не по всему файлу:
   строка `"Load clear-goal-skill…"` в секции `command` тоже содержит `goal`
   и даёт ложное срабатывание.
3. **Конфиг прочитать не удалось** — спросить один раз: «У вас установлен
   goal-плагин? 1. да · 2. нет ← по умолчанию». Ответ запомнить на сессию.
4. **Ответа нет** — Вариант B.

| Результат проверки | Что выдаём |
|---|---|
| Плагин найден (`opencode-goal-plugin`, `@bybrawe/opencode-goal` и т.п.) | **Вариант A** — команда `/goal` с флагами |
| Плагин не найден или неизвестно | **Вариант B** — markdown-контракт + предложение установить плагин |

**Вариант A — для `/goal` (с флагами goal-plugin):**
```
/goal <objective> \
  --check "<verification_command>" \
  --constraint "<constraint>" \
  --non-goal "<non-goal>" \
  --max-turns N \
  --max-minutes N
```

**Вариант B — markdown-контракт (без goal-plugin):**
```markdown
## Цель
...

### Критерий Done (проверяемый)
- [команда]
- [файл]

### Ограничения
- ...

### Не трогать
- ...

### Риски
- ...

### Отчёт
PROJECT_SUMMARY.md в корне проекта
```

### Шаг 5.5 — Gate самопроверки (обязателен)

Не выдавать цель, пока не выполнены все пункты:

- [ ] Критерий Done — **исполняемая команда**, а не описание состояния.
      Нельзя: «убедиться что работает», «проверить корректность», «всё собирается».
      Можно: `npm run build`, `test -f AGENTS.md`, `npx tsc --noEmit`
- [ ] Есть хотя бы один non-goal
- [ ] Objective — одно предложение без союза «и», соединяющего два результата
- [ ] Указаны лимиты (`--max-turns` / `--max-minutes`), хотя бы дефолтные
- [ ] Каждое значение, выбранное навыком самостоятельно, помечено `[от модели]`
- [ ] Команда проверки действительно существует в проекте (скрипт есть
      в `package.json` / `Makefile` / документации), а не выдумана

Если пункт не выполнен — **доработать цель самостоятельно**, а не задавать
новый вопрос пользователю. Вопросы закончились на Шаге 4.

### Шаг 6 — Подача
- Показать черновик цели
- Спросить: «ОК или поправить?»
- По «ОК»:
  - **Плагин есть** → выводим команду `/goal …` и поясняем, что запускать её
    как slash-команду.
  - **Плагина нет** → выводим markdown-контракт и одной строкой упоминаем, что
    для авто-продолжения существует goal-плагин. Плагины OpenCode **не ставятся
    через `npm install`** — OpenCode подтягивает их сам из конфига:

    ```jsonc
    // ~/.config/opencode/opencode.json
    "plugin": ["opencode-goal-plugin@0.11.0"]
    ```

    Версию указывать закреплённой, а не `@latest` — так требует документация плагина.

**Имена пакетов и версии не выдумывать.** Называть конкретный пакет можно, только
если он подтверждён: найден в конфиге пользователя, в документации или проверен
в реестре npm. Иначе — «поищите goal-плагин для OpenCode».
Версия выше актуальна на 2026-10-04 и со временем устареет.

## Язык: по языку пользователя

- Русские фразы → русский ответ
- `/цель` → русский ответ (детально)
- `/goalhelp` → ответ на языке проекта (коротко)
- Английские фразы → английский ответ

## Шорткат: цель уже ясна?

Если пользователь уже дал:
- Конкретный объект (файл/модуль/проект)
- Команду проверки (exit 0)
- Контекст (зачем)

→ Пропустить Шаги 1-4, сразу Шаг 5. Не спрашивать лишнее.

## Примеры

### Пример 1: Хаотичный вход с двумя целями (RU)
**Пользователь:** «Хочу починить билд в SkillCard, там ошибка рендера, ещё wiki надо синхронизировать»

**Агент:**

1. **Шаг 2.5** — распознаёт две независимые цели (разные модули, разные проверки):
   ```
   Похоже, это две цели: 1) билд SkillCard, 2) синхронизация wiki.
   1. Последовательно, сначала билд  ← по умолчанию
   2. Только билд
   3. Одной целью
   4. свой вариант
   ```
2. **Шаг 4** — разведка: в `package.json` найдены `build` и `gen:wiki-llms`,
   поэтому команда проверки не выдумывается, а предлагается вариантами.
   Пропуск «что не трогать» — средний риск (прогон автономный), спрашивается.
3. **Шаг 5** — собирается **первая** цель:
   ```
   /goal fix render error in components/SkillCard.tsx \
     --check "npm run build" \
     --non-goal "tests, other components, wiki/" \
     --max-turns 10 --max-minutes 30
   ```
4. Вторая цель (`npm run gen:wiki-llms`) выдаётся отдельно, после первой.

Ключевое: у каждой цели **своя** проверка. Если бы они были склеены через
`--check "npm run build && npm run gen:wiki-llms"`, падение wiki выглядело бы
точно так же, как несработавшая починка билда.

### Пример 2: Проясни цель (EN, короткий)
**Пользователь:** `/goalhelp I want to fix the build`

**Агент:** «What command verifies the fix? (exit 0) And what should I NOT touch?»

**Пользователь:** `npm run build, don't touch test files`

**Агент:**
```
/goal fix the build in SkillCard component --check "npm run build" --non-goal "test files and other components" --max-turns 10
```

### Пример 3: Цель уже ясна
**Пользователь:** «Напиши AGENTS.md для нового проекта clawsec»

**Агент:** (одна строка)
```
/goal create AGENTS.md for clawsec project --check "test -f AGENTS.md" --constraint "follow existing project templates"
```

### Пример 4: Анти-пример — как НЕ надо

**Плохая цель:** «Улучшить производительность приложения и заодно почистить код»

| Критерий | Что не так |
|---|---|
| S — Specific | Нет объекта: какой модуль, какой endpoint, какая операция? |
| M — Measurable | «Улучшить» не проверяется командой: нет замера, нет порога |
| T — No-waste | Нет границ → агент пойдёт рефакторить весь проект |
| Одна цель | Две независимые задачи, склеенные через «и заодно» (Шаг 2.5) |

**Что сделает агент с такой целью:** будет бесконечно «улучшать», трогая случайные
файлы, и остановится по исчерпанию лимита ходов, а не по достижению результата.
Проверить, достигнута ли цель, невозможно — значит невозможно и остановиться вовремя.

**Исправленная:**
```
/goal reduce /api/search p95 latency below 200ms in src/api/search.ts \
  --check "npm run bench:search" \
  --constraint "no schema changes" \
  --non-goal "refactoring unrelated modules, formatting" \
  --max-turns 12 [от модели] \
  --max-minutes 40 [от модели]
```

Разница: появился объект (`src/api/search.ts`), измеримый порог (p95 < 200 ms),
исполняемая проверка и явные границы. Чистка кода вынесена в отдельную цель.
Лимиты помечены `[от модели]` — их выбрал навык, а не пользователь.

## Output-шаблон (структура цели)

Всегда выдавать цель в таком формате. Перед выдачей пройти gate Шага 5.5:

```markdown
## Цель: [кратко что]

### Критерий Done (проверяемый)
- `command` (exit 0)
- `file exists/modified`
- `TASKS.md status`

### Ограничения
- `--max-turns N` `[от модели]` — если лимит не задавал пользователь
- `--max-minutes N` `[от модели]`

### Не трогать
- файлы/модули/ветки

### Риски
- зависимости, env, известные проблемы
- не определено: <что именно> — агент действует консервативно

### Проектные правила безопасности (из AGENTS.md)
- [авто-вставленные из AGENTS.md]
```

## Важные правила

1. **Не перебивать.** Сначала собрать всё, потом анализировать.
2. **Не спрашивать лишнее.** Если критерий уже заполнен — пропустить.
3. **Не больше 2 вопросов за раз.** Остальное — следующей волной, максимум 3 волны.
4. **Спрашивать только про риск от среднего.** Низкий риск закрывается дефолтом с пометкой.
5. **К каждому вопросу — 2–3 готовых варианта по цифрам** плюс «свой вариант».
6. **Определять плагин один раз за сессию.** Читать секцию `plugin` конфигов
   (проектный и глобальный, `.json` и `.jsonc`), результат кэшировать.
7. **Не выдумывать имена пакетов и команды установки.** Называть только
   подтверждённое; плагины OpenCode подключаются через конфиг, не через `npm install`.
8. **Помечать `[от модели]`** всё, что навык решил сам, а не узнал от пользователя.
9. **Проходить gate Шага 5.5 перед каждой выдачей.** Не выполнен пункт —
   доработать цель самому, а не спрашивать пользователя.

## Проектные политики безопасности

**Источник истины — `AGENTS.md` текущего проекта** (читается на Шаге 0).
Найденные там правила автоматически попадают в `constraints` и `non-goals` цели.

Список ниже — **пример, а не настройка навыка.** Замените его своими правилами.
Применять пункт отсюда можно только если он подтверждён проектом или платформой;
вслепую вставлять в цель — нельзя (правило для Windows бессмысленно на macOS).

<!-- ПРИМЕР: замените на правила своего проекта или перенесите их в AGENTS.md -->

**Универсальные (обычно применимы везде):**
- Тесты не запускать на рабочих данных проекта
- `temp/` в корне проекта для временных файлов, не системный temp
- Не коммитить секреты: ключи, токены, `.env`

**Windows / PowerShell (только если проект на Windows):**
- Удаление только в корзину (Recycle Bin, COM `Shell.Application`)
- `pwsh` вместо `powershell`
- Кодировка UTF-8 (`PYTHONIOENCODING=utf-8`)

**Unix / macOS (только если проект на Unix):**
- Удаление через `trash` / `gio trash`, не `rm -rf`

**Данные и БД (только для конвейерных проектов):**
- `selfcheck` перед записью в БД
- Миграции — отдельной целью, никогда попутно
